01 · Identidad

Logo y Marca

El logotipo del SGP combina un símbolo geométrico que abstrae la silueta de un bovino (icono de la especie dominante del dominio) con el wordmark tipográfico. El diseño es funcional en todos los contextos de la PWA: pantalla de login, splash screen, favicon y notificaciones push. Especificaciones técnicas completas (tamaños mínimos, formatos, responsive) en la sección Specs técnicas Logo.

Reglas de uso

✓ Hacer
Usar el logo completo (isotipo + wordmark) en pantallas de login, onboarding y splash screen.

Usar el isotipo solo cuando el espacio disponible es menor a 120px de ancho (favicons, notificaciones, avatares de app).

Mantener un área de protección mínima igual a la altura de la "S" del wordmark en todos los lados.
✗ No hacer
No usar emojis del sistema operativo (🐄 🐔) como sustituto del logo — no son consistentes entre plataformas.

No cambiar los colores del isotipo. El verde brand-500 es el único color aprobado para el fondo del isotipo.

No aplicar sombras, bordes o efectos adicionales sobre el logo. No deformar ni rotar.

05 · Tokens

Sistema Semáforo

Paradigma de comunicación visual central del sistema. Diseñado para usuarios con baja alfabetización digital en entornos rurales. No se usa para decoración — solo para comunicar estados reales del sistema, activos biológicos y alertas.
ESTADOS Y SU SIGNIFICADO
Verde — Normal / OK
Sistema operando correctamente. Cuenta activa, sesión válida, sensor dentro de rango, animal en estado saludable.
Amarillo — Alerta / Atención
Requiere atención pero no es crítico. Sesión por expirar, umbral de alerta alcanzado, cuenta pendiente de verificación.
Rojo — Crítico / Error
Acción requerida inmediatamente. Cuenta bloqueada, error de autenticación, sensor fuera de rango, patología detectada.
✓ Cuándo usarlo
Estados de cuenta, sesión y autenticación. Alertas de salud animal e IoT. Indicadores de sincronización offline. Resultados del modelo predictivo.
✗ No usarlo para
Categorización de contenido sin connotación de estado. Diferenciación de roles de usuario. Elementos decorativos o de branding.

✓ Siempre usar icono + texto
El color es refuerzo visual, no el único canal. Cada estado debe comunicarse también con un ícono semántico (✓ / ⚠ / ✕) y texto legible. Agregar role="alert" o aria-label en alertas críticas.
✗ No usar solo el punto de color
Un usuario con deuteranopia (ceguera al verde-rojo) no puede distinguir verde de rojo por color solo. El ícono y la etiqueta de texto son el canal accesible.

09 · Componentes

Inputs

Altura de 44px para target táctil. Los mensajes de estado (error, success) van siempre debajo del campo, nunca como tooltip flotante — el contexto rural implica pantallas pequeñas y dificultad para leer elementos superpuestos.
ESTADOS
Este campo es obligatorio y no puede estar vacío.
✓ Disponible
Este campo no se puede editar.
✓ Cuándo usar hint
Dar contexto preventivo antes de que el usuario interactúe: "Mínimo 8 caracteres". El hint es gris y pequeño, no remplaza el label.
✗ Error como tooltip
No usar tooltips flotantes para errores. En móvil son difíciles de leer. El mensaje de error siempre va debajo del campo, en rojo, visible sin interacción adicional.
10 · Componentes

Badges

Dos familias distintas con propósitos excluyentes: badges de rol (identidad del stakeholder) y badges de estado (sistema semáforo). No combinar las dos familias en el mismo elemento UI.
ROLES DE USUARIO
Administrador Productor Veterinario Contador Ing. de Campo
ESTADOS (SEMÁFORO)
Activo Pendiente Bloqueado Inactivo Info
✓ Cuándo usar badge de rol
En tablas de usuarios para identificar el rol de cada cuenta. En encabezados de perfil. En logs de auditoría para identificar quién realizó la acción.
✗ No combinar familias
No usar el color de un rol para indicar un estado. Por ejemplo, no usar el verde de "Administrador" para indicar "activo" — ese verde es del semáforo, no del rol.
11 · Componentes

Alerts

Feedback del sistema para acciones completadas, errores y estados informativos. Siempre título + descripción. Nunca solo un color sin texto — el contexto rural exige comunicación explícita, no implícita.
VARIANTES
Operación exitosa
Los cambios han sido guardados correctamente.
Atención requerida
Esta acción puede tener consecuencias. Verifica antes de continuar.
Error
No fue posible completar la operación. Intenta de nuevo.
Información
Revisa los detalles antes de proceder con la siguiente acción.
✓ Cuándo usar
Post-submit de formularios. Errores de validación de formularios completos (no solo campos individuales). Notificaciones del sistema de sincronización offline.
✗ No usar para
Reemplazar los mensajes de error de campos individuales (esos van bajo el input). No usar alerts como decoración o marketing interno. No apilar más de 2 alerts simultáneos.
12 · Componentes

Switch / Toggle

Para configuraciones binarias de estado que tienen efecto inmediato. Siempre con label y descripción — el contexto rural no permite ambigüedad. Nunca usar para confirmar acciones destructivas (usar botón + modal para eso).
VARIANTES

Recibir alertas de salud animal en tiempo real
Modo sin conexión
Activar buffer local de 72 horas (LoRaWAN)
Acceso al módulo IoT
Permiso deshabilitado para este rol
✓ Cuándo usar Switch
Configuraciones de perfil, preferencias de notificación y permisos RBAC granulares. Efecto inmediato sin necesidad de botón "guardar".
✗ Cuándo usar Checkbox
Cuando la acción no es inmediata y hay un botón "guardar" en el formulario. Para selección múltiple en listas. El Switch es para on/off instantáneo.

✓ Bandas de umbral visibles
Las zonas de color siempre están visibles aunque no haya datos recientes. El usuario de campo debe poder identificar el rango normal con un vistazo, sin interpretar números.

Registro de corrección — auditoría real vs. documentada (sept. 2026)

Origen: un reporte de re-ejecución de pruebas de accesibilidad (M01) encontró un badge de estado con contraste real de 3.3:1 donde este documento afirmaba 4.6:1 "✓ Pasa". Eso llevó a recalcular todos los pares de color del sistema con la fórmula de luminancia relativa de WCAG 2.1 en lugar de estimarlos a ojo. Resultado: de las ~20 filas documentadas en las dos tablas de contraste, solo 3 coincidían con el valor real; el resto estaba entre 0.1 y 5.0 puntos de ratio equivocado, y dos casos eran fallos reales de AA marcados como aprobados.

Proceso nuevo — para que esto no se repita

Ningún par de color se documenta como "✓ Pasa" en este sistema sin haberlo calculado programáticamente con la fórmula de luminancia relativa de WCAG 2.1 (la misma que usa axe-core). Estimar a ojo, o por familiaridad con un color parecido, es lo que produjo los 7 hallazgos de esta página.

Checklist obligatorio antes de aprobar un token de color como texto:
1) Calcular el contraste contra todos los fondos donde ese color se usará como texto — no solo el fondo "principal" del componente donde se definió.
2) Si el color se renderiza con opacity (CSS o SVG) menor a 1, calcular el contraste sobre el color ya mezclado con su fondo — no sobre el hex nominal. Un color que pasa en aislamiento puede fallar una vez aplicada la opacidad (hallazgos 3 y 4 de esta página).
3) Verificar el mismo par en modo oscuro por separado — un token sin override oscuro hereda silenciosamente el valor de modo claro (hallazgo 2).
4) Un token no se marca "✓ Pasa" en más de un fondo con un solo cálculo — brand-500 pasaba sobre blanco pero fallaba sobre brand-50 y neutral-50 (hallazgo 6).
5) Un color reusado como texto en un componente nuevo (badge, label, caption) se re-verifica ahí — no se asume que "ya se verificó en otra parte" porque el fondo cambia el resultado.
